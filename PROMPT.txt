# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: Система онлайн-аукционов "Стрелец"
## High-load Real-Time Bidding Platform

### 🎯 1. КОНЦЕПЦИЯ И БИЗНЕС-ЦЕННОСТЬ
**Стрелец** — распределенная система для проведения онлайн-аукционов в реальном времени с экстремально низкой задержкой (< 100 мс), гарантированной консистентностью данных и горизонтальной масштабируемостью.

**Бизнес-проблемы, которые решает:**
- Проведение высокочастотных аукционов (AdTech, финтех, продажа цифровых активов)
- Конкурентная борьба за ресурсы в реальном времени
- Гарантия честности торгов и прозрачности расчетов
- Защита от мошенничества и двойного расходования средств

### 🏗️ 2. АРХИТЕКТУРНЫЕ ТРЕБОВАНИЯ

#### 2.1 Основные принципы
- **Микросервисная архитектура** с четким разделением ответственности
- **Event-driven подход** через Apache Kafka
- **CQRS** для разделения моделей записи и чтения
- **Saga-паттерн** для распределенных транзакций
- **Идемпотентность** всех операций
- **Горизонтальное масштабирование** каждого сервиса независимо

#### 2.2 Ключевые нефункциональные требования
- **Latency**: P95 < 100 мс для критического пути
- **Доступность**: 99.95% uptime
- **Консистентность**: Strong consistency для финансовых операций
- **Масштабируемость**: Обработка 10K+ операций в секунду
- **Отказоустойчивость**: Автоматическое восстановление при сбоях

### ⚙️ 3. СТЕК ТЕХНОЛОГИЙ

#### 3.1 Основной стек
- **Языки**: Go (основные сервисы), Python (ML/аналитика)
- **Брокер сообщений**: Apache Kafka с топиками для каждого типа событий
- **Базы данных**:
  - PostgreSQL (транзакционные данные, бюджеты)
  - Redis (кэш, распределенные блокировки, счетчики)
  - ClickHouse (аналитика и агрегация в реальном времени)
- **Протоколы**: gRPC для внутренней коммуникации, REST для внешнего API
- **Контейнеризация**: Docker + Kubernetes
- **Мониторинг**: Prometheus + Grafana + Jaeger для трассировки

#### 3.2 Инфраструктура
- **Service Mesh**: Istio/Linkerd для управления трафиком
- **API Gateway**: Kong/Traefik
- **CI/CD**: GitLab CI/ArgoCD
- **Секреты**: HashiCorp Vault
- **Конфигурация**: etcd/Consul

### 📦 4. СЕРВИСЫ СИСТЕМЫ

#### 4.1 API Gateway (Стрелец-Шлюз)
- Единая точка входа для клиентов
- Аутентификация/авторизация (JWT, OAuth2)
- Rate limiting (токенный bucket алгоритм)
- Логирование и метрики всех входящих запросов
- Кэширование частых запросов

#### 4.2 Auction Engine (Стрелец-Аукцион)
**Ответственность**: Проведение аукционов по правилам
- Поддержка типов аукционов: First-price, Second-price (Vickrey)
- Таймеры завершения аукционов
- Определение победителя по алгоритму
- Публикация событий: `AuctionStarted`, `NewLeader`, `AuctionFinished`

#### 4.3 Bidder Service (Стрелец-Ставки)
**Ответственность**: Прием и валидация ставок
- Валидация ставки (формат, размер, время)
- Проверка наличия средств через Budget Service (синхронно)
- Отправка ставки в Auction Engine
- Идемпотентная обработка дублей
- Паттерн Circuit Breaker для вызовов Budget Service

#### 4.4 Budget Service (Стрелец-Бюджет)
**Ответственность**: Управление балансами участников
- Списание/резервирование средств
- Гарантия консистентности при конкурентном доступе
- **Алгоритмы**:
  - Оптимистичные блокировки через versioning
  - Распределенные транзакции через Saga
  - Компенсирующие транзакции при откате
- Экспорт событий: `FundsReserved`, `FundsCharged`, `FundsReleased`

#### 4.5 Analytics Aggregator (Стрелец-Аналитика)
**Ответственность**: Агрегация данных в реальном времени
- Потребление событий из Kafka
- Подсчет метрик: CTR, win rate, средняя цена
- Агрегация по временным окнам (1мин, 5мин, 1ч)
- Экспорт данных в ClickHouse для дашбордов

#### 4.6 Notification Service (Стрелец-Уведомления)
- WebSocket соединения для реальных уведомлений
- Отправка email/push о победах
- Очередь с приоритетами для критических уведомлений

### 🔄 5. ПОТОКИ ДАННЫХ

#### 5.1 Основной поток ставки
```
1. Клиент → API Gateway → Bidder Service (HTTP/2)
2. Bidder Service → Budget Service (gRPC): Резервирование средств
3. Budget Service → PostgreSQL: Атомарное обновление баланса
4. Bidder Service → Kafka: Событие `BidSubmitted`
5. Auction Engine (consumer Kafka) → Обработка ставки
6. Auction Engine → Kafka: Событие `BidAccepted` или `BidRejected`
7. Notification Service → Клиент: Результат через WebSocket
```

#### 5.2 Поток завершения аукциона
```
1. Auction Engine → Определение победителя
2. Auction Engine → Kafka: `AuctionFinished`
3. Budget Service (consumer) → Финальное списание средств
4. Notification Service → Уведомление победителю и продавцу
5. Analytics Aggregator → Обновление агрегированных данных
```

### 🛡️ 6. ГАРАНТИИ И КОМПРОМИССЫ

#### 6.1 PACELC-компромиссы
- **Бюджетные операции**: PC/EC (Консистентность важнее задержки)
- **Прием ставок**: PA/EL (Доступность важнее, eventual consistency допустима)
- **Аналитика**: PA/EL (Можно потерять часть событий, но система должна работать)

#### 6.2 Механизмы обеспечения надежности
- **Retry с экспоненциальной backoff** для всех внешних вызовов
- **Dead Letter Queue** для неудачных сообщений
- **Health checks** и readiness/liveness пробы
- **Graceful shutdown** всех сервисов

### 📊 7. МОНИТОРИНГ И АНАЛИТИКА

#### 7.1 Обязательные метрики
- Задержка обработки ставки (гистограмма)
- Количество активных аукционов
- Коэффициент выигранных ставок (win rate)
- Ошибки по типам (валидация, недостаток средств, таймауты)
- Загрузка Kafka (лаг потребителей)

#### 7.2 Дашборды Grafana
1. **Общая статистика**: RPS, успешные/неуспешные ставки
2. **Латентность**: P50, P95, P99 по каждому сервису
3. **Бизнес-метрики**: Средний размер ставки, распределение побед
4. **Инфраструктура**: Загрузка CPU/памяти, лаг репликации БД

### 🧪 8. ТЕСТИРОВАНИЕ

#### 8.1 Типы тестов
- **Юнит-тесты**: 90% покрытие для бизнес-логики
- **Интеграционные тесты**: Docker Compose с полным стэком
- **Нагрузочное тестирование**: k6/Яндекс.Танк, сценарии:
  - Пиковая нагрузка (10K RPS)
  - Длительная нагрузка (1 час, 1K RPS)
  - Деградация сервисов (отказ Budget Service)
- **Chaos Engineering**: отключение случайных pod'ов в Kubernetes

#### 8.2 Тестовые сценарии
- Конкурентные ставки на один лот
- Исчерпание бюджета участника
- Сбой сети между сервисами
- Повторная отправка одинаковой ставки (идемпотентность)

### 🚀 9. ПЛАН ВНЕДРЕНИЯ

#### Этап 1: MVP (2-3 недели)
- Монолит с основными функциями
- In-memory хранилище
- Без распределенных транзакций

#### Этап 2: Распределенная система (4-5 недель)
- Выделение Budget Service с PostgreSQL
- Внедрение Kafka для асинхронной коммуникации
- Saga для управления транзакциями

#### Этап 3: Масштабирование (2-3 недели)
- Горизонтальное масштабирование каждого сервиса
- Кэширование в Redis
- Настройка мониторинга

#### Этап 4: Оптимизация (1-2 недели)
- Профилирование и оптимизация горячих путей
- Настройка autoscaling в Kubernetes
- Load testing и тюнинг

### 🔮 11. ДОРОЖНАЯ КАРТА ДЛЯ РАЗВИТИЯ

#### 11.1 Short-term (после MVP)
- ML-модель для предсказания оптимальной ставки
- A/B тестирование алгоритмов аукциона
- Геораспределение (CDN для WebSocket)

#### 11.2 Long-term
- Поддержка сложных аукционов (голландский, тендеры)
- Интеграция с блокчейном для аудита
- Predictive autoscaling на основе ML

### 🎖️ 12. КРИТЕРИИ УСПЕХА

#### Технические метрики
- P95 latency < 100 мс в течение 24/7
- Zero data loss для финансовых операций
- Восстановление < 5 минут при сбое любого сервиса

#### Бизнес-метрики
- Обработка 1M+ ставок в день
- Среднее время отклика системы < 50 мс
- Доступность 99.95% в SLA
